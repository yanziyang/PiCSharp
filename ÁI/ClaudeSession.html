The finding

Migrating to .NET 10 and keeping near-full plugin compatibility are mutually exclusive requirements. I cloned earendil-works/pi and read the extension subsystem rather than working from docs, and the reason is structural:

Pi's plugin contract is an in-process JavaScript object graph, not a wire protocol. loader.ts uses jiti to transpile extension TypeScript at runtime and execute it in the agent's own Node process. Handlers get live references — the TUI instance, SessionManager, ModelRegistry, an AbortSignal, callback functions — and are expected to mutate event.input in place. Extensions also import node:fs, node:child_process and arbitrary npm packages directly.

No C# program reproduces that without embedding Node.js — at which point the migration is nominal. I assessed all four JS-in-.NET mechanisms: Jint and ClearScript both fail outright (V8 is a JS engine; node:* modules are Node's, not V8's). Only node-api-dotnet and a Node sidecar work, and both keep Node in the runtime.

Recommendation: build a .NET 10 client on Pi's existing pi-protocol v1 seam (which Pi already ships and supports), running Pi unmodified as a sidecar. ~4–8 engineer-months against 55–85 for a rewrite, and it preserves 100% of the ecosystem.

Two things worth flagging about the brief itself: the monorepo publishes ten packages, not the three listed — 123,629 LOC production plus 115,921 LOC of tests. And I measured extension coupling empirically across Pi's 85 bundled extensions: 41% render into the TUI, which is the practical ceiling on any out-of-process bridge and the reason even the sidecar-based "true migration" (Option B) lands near 59% compatibility rather than "nearly full".
