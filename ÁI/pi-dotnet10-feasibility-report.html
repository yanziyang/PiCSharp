Technical Feasibility Assessment

Migrating the Pi Coding Agent to .NET 10

An evidence-based assessment of porting Earendil's Pi coding agent from its TypeScript monorepo to .NET 10, against a requirement of near-full compatibility with the existing Pi ecosystem — extensions, skills, prompts, themes and packages.

Prepared29 August 2026
Subjectearendil-works/pi @ v0.84.4
Target.NET 10 (LTS)
BasisDirect source analysis
ClassificationEngineering decision input

Verdict: not feasible as specified — but a better-shaped option exists

A rewrite of Pi in C# that preserves near-full plugin compatibility cannot be delivered, because "plugin compatibility" in Pi is defined by an in-process JavaScript contract: extensions are TypeScript modules transpiled at runtime and handed live object references to the terminal UI, session manager and agent runtime, with unrestricted access to Node.js built-ins. No C# program reproduces that contract without embedding Node.js itself — at which point the migration is nominal.

Recommended instead: build a .NET 10 client on Pi's own versioned RPC protocol (pi-protocol v1), which Pi already ships and supports. This preserves 100% of the ecosystem, costs an estimated 4–8 engineer-months rather than 55–85, and carries low delivery risk.

1Executive summary

The bottom line, before the detail.

Pi is a self-extensible coding agent harness published by Earendil as an MIT-licensed TypeScript monorepo. The brief was to assess migrating it to .NET 10 while retaining near-full compatibility with the Pi ecosystem, especially plugins.

Direct analysis of the repository at v0.84.4 establishes three findings that determine the answer.

Finding 1 — The system is larger than the three packages named in the brief

The brief cites three packages. The monorepo publishes ten, totalling 123,629 lines of production TypeScript and a further 115,921 lines of tests across 472 test files. The named pi-coding-agent alone is 60,960 lines — roughly half the production codebase — and it is the package that hosts the extension API.

Finding 2 — Plugin compatibility is an in-process JavaScript contract, not a protocol

Pi loads extensions with jiti, transpiling TypeScript at runtime and executing it inside the agent's own Node.js process. An extension's default-exported factory receives an ExtensionAPI object spanning 157 exported types and 27 event categories. Handlers are given live references — the TUI instance, the SessionManager, the ModelRegistry, an AbortSignal, and callback functions — and are expected to mutate some of them in place. Extensions also import node:fs, node:child_process, node:zlib and arbitrary npm packages directly.

None of that is expressible as a serialised message contract, and reproducing it in C# means reproducing a JavaScript runtime, not translating an interface.

Finding 3 — Roughly two-fifths of extensions are coupled to the terminal UI

Measured across the 85 extension files bundled in the repository: 41% register custom TUI components, renderers, widgets, editor factories or autocomplete providers; 58% call interactive UI dialogs; 26% call Node built-ins directly.

Only the last of those is a hard boundary. The component contract turns out to be four members, of which the substance is render(width: number): string[] — extensions emit arrays of pre-styled strings, not a widget tree. That crosses a process boundary; what it costs is per-frame IPC during streaming. The unconditional blocker remains the Node.js runtime itself, which no C# host provides.

Conclusion on the brief as written

"Migrate to .NET 10" and "near-full plugin compatibility" are mutually exclusive requirements. Any rewrite that removes Node.js from the runtime removes the ecosystem with it. Any approach that keeps the ecosystem keeps Node.js — and is therefore not a migration in the sense the brief implies.

What is feasible, and recommended

Pi already separates its runtime from its front-end: pi-protocol (a versioned, typebox-schema'd wire format with CBOR and JSON codecs), pi-server (session host) and pi-client (client SDK). That seam is the supported integration point, and a .NET client over it delivers what most .NET-shaped goals actually require: a first-class C# API onto a fully-capable Pi, with the entire ecosystem intact and upstream releases consumed rather than chased.

Estimated 4–8 engineer-months, 2–4 calendar months, low risk — against 55–85 engineer-months and 18–24 months for a full rewrite that would still forfeit every existing plugin.

3What Pi actually is

The system under assessment, at its real scale.

Pi describes itself as a minimal, extensible agent harness. "Minimal" refers to its core policy surface, not its implementation: Pi deliberately omits MCP support, built-in sub-agents, permission dialogs, plan mode and to-do tracking, expecting users to supply them as extensions. That design choice is important to this assessment, because it means features that other agents implement internally are, in Pi, implemented in the plugin layer. The plugin layer is therefore not peripheral — it is where much of the product lives.

The ecosystem surface a migration must preserve

"The Pi ecosystem" is four distinct artefact types, distributed from npm, git repositories or local paths and declared through a pi key in package.json:

  • Extensions — TypeScript modules with access to tools, commands, keybindings, events and the UI layer. The hard case.
  • Skills — Markdown capability packages loaded on demand. Portable: content, not code.
  • Prompt templates — reusable Markdown prompts invoked as /name. Portable.
  • Themes — JSON colour definitions. Portable, subject to a compatible renderer.

Three of the four are declarative and would port without difficulty. The fourth carries the engineering value and is the subject of the next section.

4The binding constraint

Why the plugin contract, not the line count, decides this question.

Rewriting 123,629 lines of TypeScript in C# is expensive but tractable. The reason a Pi migration is qualitatively harder than a large port is that Pi's public contract with its ecosystem is a live JavaScript object graph, and the ecosystem is written against that graph rather than against a message schema.

The loading path

Pi's loader.ts constructs a jiti instance and imports the extension module directly:

// packages/coding-agent/src/core/extensions/loader.ts import { createJiti } from "jiti/static"; // … const jiti = createJiti(import.meta.url, { /* aliases */ }); const module = await jiti.import(extensionPath, { default: true });

There is no build step, no serialisation boundary and no sandbox. The extension's exported factory is invoked with the API object and runs with the same privileges as the agent.

// The contract every Pi extension is written against import type { ExtensionAPI } from "@earendil-works/pi-coding-agent"; export default function (pi: ExtensionAPI) { pi.on("tool_call", async (event, ctx) => { if (event.toolName === "bash" && event.input.command?.includes("rm -rf")) { const ok = await ctx.ui.confirm("Dangerous!", "Allow this?"); if (!ok) return { block: true }; // veto, synchronously honoured } }); }

Five properties that do not survive translation

  1. Live object references. ExtensionContext exposes sessionManager, modelRegistry, model, a live AbortSignal, and methods such as abort(), compact() and getSystemPrompt(). Command contexts go further, accepting callback functions — newSession({ setup: (sessionManager) => …, withSession: (ctx) => … }). Passing a closure across a process boundary requires inverting the call pattern entirely.
  2. In-place mutation. The tool_call contract states that arguments are modified by mutating event.input directly, with the return value reserved for blocking. Reference mutation has no equivalent over a message channel without redefining the contract.
  3. Synchronous veto semantics. Handlers block execution: a returned { block: true } stops the tool. Latency that was a function call becomes a network round-trip, changing timing behaviour extensions depend on.
  4. UI component registration. Extensions register renderers, widgets, overlays, editor factories and autocomplete providers against the TUI instance. The contract is narrow — render(width): string[], plus optional input handling and cache invalidation — so components are portable in principle. What binds them is the rate: the renderer calls render every frame, and an editor factory sees every keystroke.
  5. Unrestricted Node.js access. Extensions import node:fs, node:child_process, node:zlib, node:readline, node:module and arbitrary npm dependencies. Pi documents that it deliberately ships no permission system, directing users to containerisation instead. The security model assumes trusted, fully-privileged in-process code.

These are the extensions Earendil ships as reference implementations — sub-agents, plan mode, permission gates, path protection, SSH execution, sandboxing, status lines, and several games. Those 41% do not merely observe the UI, they render into it — but they do so by returning lines of text, which is why an out-of-process bridge degrades them rather than breaking them.

A design choice worth noting

Pi deliberately excludes MCP support — the obvious out-of-process extension mechanism — in favour of in-process TypeScript extensions. This is not an oversight the migration can route around; it is a stated architectural position. Pi's extensibility model is intentionally language-bound.

5Could .NET simply run the plugins?

Assessing every mechanism for executing Pi extensions from a .NET host.

If .NET could execute the existing TypeScript extensions, compatibility would be preserved and the question would reduce to a normal port. Four mechanisms exist. All were assessed against the actual requirement: run unmodified Pi extensions, including those importing node:fs and node:child_process.

MechanismWhat it isNode.js API supportVerdict
JintPure-C# ECMAScript interpreter None — language only, no Node built-ins, no module resolution Fails Cannot load an extension that imports node:fs
ClearScript (V8)Embeds the V8 engine in .NET None — V8 is the JS engine; node:* modules are Node's, not V8's Fails You would have to reimplement Node's standard library
node-api-dotnetMicrosoft's in-process .NET ⇄ JS interop over Node-API Full — it hosts a real Node.js runtime Works, nominally Node.js remains a hard dependency; still public preview
Node.js sidecar processSeparate Node process, spoken to over IPC Full — genuine Node runtime Works Clean boundary; the basis of the recommendation

The two mechanisms that work do so by keeping Node.js in the runtime. This is the decisive point: no option removes Node.js while retaining plugins. The genuine choice is not "Node or .NET" but where the boundary sits — and a process boundary (sidecar) is preferable to an in-process one (node-api-dotnet), because it is simpler to supervise, isolate, containerise and version, and it does not depend on a preview-status interop layer.

A note on jiti specifically

Even with a JavaScript engine available, extensions arrive as TypeScript. Pi's loader transpiles them at runtime with jiti and resolves bare imports against Pi's own bundled modules. A .NET host would need to reproduce that transpilation and module-resolution behaviour as well — which is, again, most easily done by running Node.

What .NET 10 genuinely brings

Strengths that are real

  • LTS support window — .NET 10 shipped November 2025 with support to November 2028, against Pi's pre-1.0, 2.7-releases-per-week cadence.
  • Microsoft.Extensions.AI — a mature IChatClient abstraction that solves the same problem as pi-ai for .NET-native call sites.
  • Native AOT — smaller, faster-starting single binaries; competitive with Pi's Bun-compiled executables.
  • Enterprise fit — DI, configuration, health checks, OpenTelemetry, Entra ID and Azure integration are idiomatic rather than bolted on.
  • Static typing and tooling at the host layer, where correctness matters most.

What .NET does not solve

  • No terminal-UI peer to pi-tui. Spectre.Console is excellent for CLI output, not for a differential full-screen renderer with inline image protocols.
  • No path to running TypeScript extensions without Node.js.
  • No answer to provider breadth — the 47-provider long tail is bespoke work regardless of language.
  • No relief from upstream drift. A port must track a fast-moving pre-1.0 project indefinitely.

7Effort model

The arithmetic behind the estimates, stated so it can be challenged.

Estimates use a throughput assumption of 2,000–3,000 lines of production code per engineer-month for a faithful cross-language port — a rate that accounts for reading and understanding the source, writing idiomatic C#, and debugging behavioural differences — and ~4,000 LOC/engineer-month for test translation, which is more mechanical. These are mid-range figures for disciplined teams on well-structured code; Pi's code is well-structured.

ScopeLOCRate (LOC/eng-mo)Engineer-months

Rounding for uncertainty in both directions gives 55–85 engineer-months for a full rewrite. With a team of six this is roughly 13 months of pure porting; adding integration, behavioural parity chasing and the moving-target problem below puts realistic time-to-parity at 18–24 calendar months.

The moving-target multiplier

Pi published 43 versions in the 113 days to 28 August 2026 — about 2.7 releases per week, at version 0.84.4, still pre-1.0. Over an 18-month rewrite, upstream would ship on the order of 200 further releases, including breaking changes that pre-1.0 semver permits. A port does not converge on a stationary target; parity is a treadmill, and the fork begins diverging on day one.

This risk is the single strongest argument against Options A and D, and it is structural rather than a matter of team quality.

By contrast, the recommended option is scoped to pi-client (1,225 LOC) plus protocol types (1,236 LOC), host supervision, and a conformance suite — roughly 4–8 engineer-months, with upstream drift absorbed by a versioned protocol rather than by re-porting.

8Strategy options

Four candidate approaches, compared on the criteria that matter.

Option A — Full C# rewrite

Port all ten packages to .NET 10 and define a new C#-based extension API. 55–85 engineer-months; 18–24 months.

This is what the brief literally asks for, and it forfeits the requirement the brief also states. Every existing extension breaks; the 50+ community packages do not come across; Earendil's own reference extensions would need reimplementation. The team would additionally own a from-scratch terminal renderer and 47 provider integrations, while chasing a codebase that ships twice a week. Not recommended.

Option B — .NET host with a Node extension sidecar

Rewrite the host in C# but keep extensions running in Node, bridged by a new out-of-process extension protocol. 30–45 engineer-months; 12–18 months.

This is the only approach that is both a genuine migration and retains substantial compatibility. Event-driven, tool-registering and dialog-using extensions bridge cleanly, and so do UI components — render(width): string[] crosses a process boundary without difficulty. Realistic functional compatibility is high, on the order of 90%. The constraint is not correctness but rate: the renderer calls every component each frame, and an editor factory sees every keystroke, so those paths degrade over IPC. The project still ships two runtimes and must maintain a bespoke bridge against upstream changes to a 157-type API. Viable; the strongest fallback if Option C proves insufficient.

Option C — .NET client over pi-protocol Recommended

Build a first-class C# client against Pi's existing versioned RPC protocol, running Pi unmodified as a managed child process. 4–8 engineer-months; 2–4 months.

Pi already ships this seam and supports it as an integration path: pi-protocol defines versioned schemas with CBOR and JSON codecs, pi-server hosts sessions, and pi-client demonstrates the client side in 1,225 lines. Porting that client to C# gives .NET applications an idiomatic API onto a fully-capable Pi — every extension, skill, prompt and theme intact — while upstream releases are consumed by version-pinning rather than chased by re-porting. Recommended.

Option D — A .NET-native agent, without Pi compatibility

Build a new agent in C# on Microsoft.Extensions.AI, borrowing Pi's ideas but none of its contracts. 12–20 engineer-months; 6–10 months.

Legitimate and honest if the real objective is a .NET coding agent rather than Pi on .NET. It is cheaper than a faithful port precisely because it drops the parity obligation, and .NET's AI stack is now good enough to make it credible. It simply is not a migration, and should not be presented as one. Consider only if plugin compatibility is genuinely not required.

9Recommendation

What to build, and why this shape.

Recommendation

Adopt Option C: a .NET 10 host built on Pi's existing pi-protocol seam, with Pi running unmodified as a supervised Node.js sidecar. Treat Option B as a deferred upgrade path, to be triggered only if a .NET-native terminal UI later becomes a hard requirement.

The reasoning is that this shape gets the benefits actually sought from .NET without paying for the one thing .NET cannot provide.

  • The ecosystem is preserved in full. Extensions run on the runtime they were written for. There is no compatibility percentage to negotiate, because nothing is being reimplemented.
  • Upstream velocity becomes an asset. New providers, features and fixes arrive by bumping a pinned version. Under a rewrite, the same velocity is a liability.
  • .NET owns the parts .NET is good at. Hosting, DI, configuration, auth, observability, Azure integration and the application's own domain logic are all C#. Microsoft.Extensions.AI is available for model calls the application makes itself, independently of Pi.
  • The commitment is small and reversible. Phases 0 and 1 are cheap to abandon, and nothing forks Pi. A failed spike costs weeks, not quarters.
  • It does not preclude Option B. Extending the protocol with component-tree messages later is additive; work built against the protocol keeps working.

What this does not give you

Stated plainly, so the decision is made with open eyes:

  • Node.js stays in the runtime image. If the objective is eliminating the Node dependency, Option C does not achieve it — and neither does anything else that keeps plugins.
  • Extensions remain TypeScript. .NET teams wanting to author extensions still write TypeScript. The durable fix is an out-of-process extension protocol contributed upstream, which would benefit every language; that is a conversation with Earendil, not a migration task.
  • The terminal UI remains Pi's. A .NET-native TUI is Option B territory and should be costed separately if it is required.
A strategic suggestion

If .NET-authored extensions matter over the long term, the highest-leverage move is not a fork — it is proposing an out-of-process extension protocol to the Pi project itself. Pi already has the protocol infrastructure (pi-protocol, pi-server, pi-client) to support one, the project is MIT-licensed and actively developed, and such a contribution would open extension authoring to every language rather than just C#.

Four phases, each ending in a decision gate with a working deliverable.

The one framing to avoid

Do not adopt Option A on the assumption that plugin compatibility can be recovered later with a shim. It cannot. The compatibility surface is 157 types of in-process JavaScript contract, and once the host is C#, every one of them has to be re-offered through a boundary that changes their semantics. Compatibility is a decision made at the start of this work, not a feature added at the end.
