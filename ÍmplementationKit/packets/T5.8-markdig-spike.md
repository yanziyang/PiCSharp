## This packet produces findings, not a port

**Do not port `components/markdown.ts` in this packet.** The deliverable is an updated
`docs/spikes/markdig-divergence.md` and a go/no-go recommendation. If the answer is go, the port is
the next packet and will be written against your findings.

That distinction is the whole point of the packet. A spike that quietly becomes an implementation
loses the thing it was for: the chance to find out cheaply that the approach is wrong.

## Where things stand

`docs/dependencies.md §3` approves Markdig (BSD-2-Clause) to replace `marked`. Its one stated
condition — support for the hook `registerMarkdownTransformer` needs — **is already satisfied and
closed**: the transformer is `(markdown: string, context) => string`, so it operates on source text
upstream of parsing and never sees a token.

A preliminary run comparing `marked@18.0.5` against `Markdig 0.44.0` over 15 hand-picked constructs is
recorded in `docs/spikes/markdig-divergence.md`. Ten map cleanly. Four diverge:

1. `del` is `EmphasisInline` with a delimiter char, not a distinct node
2. `escape` tokens are erased into literal text
3. `autolink` is `AutolinkInline`, not the `link` path `markdown.ts` handles
4. soft line breaks inside blockquotes survive as nodes instead of being joined

None is fatal. The preliminary verdict is **viable**, and nothing yet argues for porting `marked` or
hand-writing a parser.

## Objectives

### 1. Replace the hand-picked inputs with the real ones

The 15 constructs were chosen by me from knowledge of where CommonMark implementations disagree. They
are not the inputs that matter. **Harvest the markdown sources the 81 upstream cases actually use**
from `reference/pi/packages/tui/test/markdown.test.ts` and run those through both parsers.

That is where the long tail lives, and it is the only sample with a claim to being representative.

### 2. Enumerate every divergence, not just the count

For each, record: the input, both type streams, and — the part that matters — **whether it changes
what the renderer would emit**. A structural difference the renderer never observes is not a finding;
a structural difference that moves a line break is.

### 3. Close the two open questions

- **`escape`**: `markdown.ts` has `case "escape"`. Read what that branch does. If it renders the
  escaped character and nothing more, Markdig's resolved literal is equivalent and the divergence is
  free. If it does anything else, say what the adapter must recover.
- **Blockquote soft breaks**: this is the one divergence with direct visual consequences, because the
  renderer wraps to a width. Determine which behaviour upstream's tests actually require.

### 4. Prove the two custom behaviours are expressible

Not by argument — **by writing them** in the spike project:

- **Strict strikethrough.** Upstream overrides `Tokenizer.del` with `STRICT_STRIKETHROUGH_REGEX` so
  that `~single~` is not strikethrough. Both parsers treat it as strikethrough by default, so the
  same override is needed. Show it working on the Markdig side.
- **Inline and block LaTeX.** `$$…$$`, `\(…\)` and friends, currently `TokenizerExtension`s. The
  tokenizing logic in `markdown.ts` is already hand-written — `tokenizeInlineLatex`,
  `findClosingDelimiter`, `isEscaped` — so the question is only whether Markdig's extension model has
  a place to host it. Show that it does.

If either cannot be expressed, that is the finding, and it is a go/no-go input.

### 5. Write the adapter mapping

The output the port needs is a table: for each of the **19 token types `markdown.ts` inspects**, the
Markdig node type and any property checks required to distinguish it. That table is what the next
packet implements.

## One standing instruction

**Anything not delivered, or any instruction overridden, must be named in the PR.** The specific risk
in a spike is the opposite of the usual one: not silent omission, but silent scope growth. If you find

early than bundled into a port that is hard to unwind if the answer turns out to be no.
