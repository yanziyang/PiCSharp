# `T1.2` — Port `pi-protocol` to `Pi.Protocol`

**Wave:** 1  **Delegation fit:** A  **Depends on:** nothing (foundation project)

---

## Objective

Port the `@earendil-works/pi-protocol` package from TypeScript to C#. This is the versioned wire
protocol shared by the client and server: schemas, CBOR codec, and frame encoding.

## Oracle

1. **Ported upstream tests.** Port every case from the three test locations above into
   `tests/Pi.Protocol.Tests/`, preserving test names verbatim so a failure maps back to an upstream
   case. No case may be weakened, narrowed, or deleted. If one genuinely cannot be ported, mark it
   `[Fact(Skip = "specific reason")]` and list it in the PR — note that CI enforces a skip budget of
   zero, so any skip fails the build until the budget is raised with justification.

2. **Byte-level encode equivalence.** For a representative set of messages covering every branch of
   `ClientMessage` and `ServerMessage`, the bytes produced by `EncodeClientMessage` /
   `EncodeServerMessage` must be identical to those produced by the TypeScript implementation.
   Commit the expected byte vectors as fixtures under `tests/Pi.Protocol.Tests/`.

3. **Round-trip.** Every schema round-trips: encode → decode → deep-equal to the original, including
   optional-field presence and absence.

## Known hazards

These will bite. They are called out because the cost of getting them wrong is a wire-incompatible
client that passes its own unit tests.

- **Upstream ships its own CBOR codec.** `cbor/encoder.ts` and `cbor/decoder.ts` are 384 LOC of
  hand-written encoding with specific canonical-form choices. `docs/dependencies.md` lists
  `System.Formats.Cbor` as the in-box replacement, but that is an *assumption pending proof*. Port the
  upstream encoder's behaviour and verify byte-identical output against oracle 2 first. If
  `System.Formats.Cbor` produces identical bytes for the full fixture set you may use it and say so in
  the PR; if it does not, port the encoder directly. **Do not silently substitute it.**

- **The frame format is exact.** `FRAME_HEADER_LENGTH = 4`, `MAX_UINT32`, and
  `PAYLOAD_BLOCK_SIZE = 64 * 1024`. Reproduce the header's byte order exactly as `framing.ts` writes
  it — read the code, do not assume big-endian.

- **The limits are part of the security contract, not tuning.** `DEFAULT_MAX_CBOR_BYTE_LENGTH`
  (16 MiB), `DEFAULT_MAX_CBOR_CONTAINER_LENGTH` (1,000,000), `DEFAULT_MAX_CBOR_DEPTH` (64),
  `DEFAULT_MAX_FRAME_LENGTH` (16 MiB) guard untrusted payloads. Keep the values, keep the enforcement
  points, and keep the errors they raise.

- **`StrictObject` means `additionalProperties: false`.** Unknown fields must be *rejected*, not
  ignored. `System.Text.Json` ignores unknown members by default — that is a wire-compatibility bug
  here. Use `JsonUnmappedMemberHandling.Disallow` or equivalent, and test it.

- **`JsonValueSchema` is recursive** (`Type.Cyclic`). Model it as a discriminated union that supports
  arbitrary nesting, bounded by the depth limit above.

- **`undefined` is not `null`.** See `docs/translation-patterns.md §1`. Never write a field upstream
  omits; never omit one upstream writes. Round-trip tests must assert the exact key set.

- **Preserve error type names and messages.** `CborError`, `FrameError`, `ProtocolValidationError`
  are observable. Map them to a `PiException` hierarchy keeping the names and message text.

- **Streaming decoders are stateful.** `FrameDecoder`, `ClientMessageDecoder` and
  `ServerMessageDecoder` accept partial input across calls. A frame may be split at any byte
  boundary, including inside the 4-byte header. Test that explicitly.

## Out of scope

- Do not port `packages/client` or `packages/server` — those are wave 4 (T4.1, T4.2).
- Do not add any NuGet package. If you believe one is required, stop and report it; additions need an
  approved entry in `docs/dependencies.md`.
- Do not change the wire format, the schema shapes, or the protocol version, even if something looks
  suboptimal. Port it faithfully and note the observation in the PR.
- Do not add a JSON-schema emitter. Tool-parameter schemas are T2.1's problem, not this one.

## Conventions

Follow `AGENTS.md` at the repository root, and `docs/translation-patterns.md` for every TS→C#
construct. Where the conventions and the TypeScript source conflict, **the source wins** — and say so
in the PR.

Target namespace `Pi.Protocol`. Keep a 1:1 file correspondence with the source where practical
(`framing.ts` → `Framing.cs`, `cbor/encoder.ts` → `Cbor/CborEncoder.cs`); state any deviation in the
PR description.
