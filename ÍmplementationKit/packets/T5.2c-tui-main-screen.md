## Why this is next, and what went wrong last time

**`src/` has no concrete TUI.** `TuiBase.DoRender` is abstract, and the only subclass in the
repository is `TestTui` in `tests/Pi.Tui.Tests/TuiTestSupport.cs`. That is not a design choice — it
is fallout from an error in the T5.2b packet, which is worth stating plainly because it shapes this
one:

> T5.2b asked for all 27 cases in `tui-render.test.ts` while declaring `tui-main-screen.ts` out of
> scope. Every one of those 27 cases constructs `TuiMainScreen`. `tui.ts` has no upstream suite of
> its own; it is exercised through the main screen. The packet asked for tests of a file it had
> forbidden.

The delivery worked around it by reimplementing main-screen behaviour inside `TestTui` — including
`isTermuxSession()` — and porting 20 cases against that. Those tests exercise the real `TuiBase`
render loop, so they are not worthless, but nothing they assert is shipped code.

This packet closes that. It is also the highest-leverage file left in wave 5: `TuiMainScreen` is
constructed by **twelve** upstream test files totalling ~380 cases. This packet claims 99 of them.

## Hazards

### 1. Do not leave two implementations standing

When the real class exists, `TestTui` must stop carrying product logic. Its `DoRender` currently
holds the Termux check that upstream ships in `tui-main-screen.ts:109`. Move that to the real class
and reduce `TestTui` to a fixture, or delete it outright.

The 20 existing `tui-render` cases must construct the real `TuiMainScreen`. **Re-point them; do not
write parallel copies.** If two classes both implement the render loop, the suite proves nothing
about the one that ships.

### 2. The seam grows by exactly four trivial members

`tui-main-screen.ts` needs `deleteKittyImage`, and `tui-cell-size-input.test.ts` needs the cell and
capability accessors. All four are trivial:

```ts
deleteKittyImage(id)       -> `\x1b_Ga=d,d=I,i=${id},q=2\x1b\\`   // one line, no encoder
getCellDimensions()        -> the value set by setCellDimensions
resetCapabilitiesCache()   -> clears the cache
setCapabilities(caps)      -> test override
```

**Do not implement `renderImage`, `getImageDimensions`, or any protocol encoding.** Those are T5.5,
and they are the reason the 7 Kitty cases in `tui-render.test.ts` stay skipped: they build a real
`Image` component, which needs the encoder. `deleteKittyImage` needs none of it — it is a string.

### 3. `parseKittyImageHeader` belongs to this file, not to the seam

It is defined at `tui-main-screen.ts:80`, with `extractKittyImageIds` and `extractKittyImageRows`
beside it. Port them here. The image *bookkeeping* — which ids were drawn, how many rows a placement
reserves — is main-screen logic and is in scope even though the 7 cases that render real images are
not.

### 4. The overlay cases are the first test of code that shipped untested

69 of the 99 are overlay tests. `tui.ts`'s overlay implementation — `OverlayOptions`, `OverlayHandle`,
anchors, margins, percentage `SizeValue` — landed in T5.2b with **zero** upstream coverage, because
the cases that cover it all go through the main screen.

So expect failures here, and treat them as findings rather than obstacles. If a ported overlay case
fails, that is a T5.2b defect: report it in the PR with the upstream expectation and the actual C#
behaviour, then fix it in a **separate commit** from the port.

### 5. Do not read `TERMUX_VERSION` from the render thread

The Termux case is being un-skipped, and it failed intermittently before for a specific reason:
`DoRender` read the process-global environment variable on the render thread while the test thread
set and restored it around the test body.

Read the environment **once at construction**, or inject it. Do not re-read a process global on every
render. Upstream calls `isTermuxSession()` per render safely only because Node renders on a
single-threaded event loop — that assumption does not survive the port, and this is the second flake
in this package traced to it. Say in the PR which approach you took.

### 6. Redraw logging touches the filesystem

`tui-main-screen.ts` imports `node:fs` and `node:path` for redraw logs, and
`writes redraw logs to the provided directory` is one of the 21 cases. Use a temp directory per test
and clean up; do not write into the repository.

### 7. Standing rules

- **`undefined` is not `null`** — `translation-patterns.md §1`.
- Where a test needs to observe async work, wait on the **condition**. `MemoryTerminal.WaitForRenderAsync`
  is now settle-based; use it rather than adding fixed delays. A delay that is itself the behaviour
  under test is the one exception.
- **Where a hazard here contradicts the TypeScript source, the source wins** — and **say so in the PR**.

## One standing instruction

**The tests ship in the same PR as the code**, and **anything not delivered must be named in the PR.**
Seven packets running, the PR text has not once mentioned an omission or an override, and each has
been found by diffing afterwards. T5.2b is the clearest case yet of why that costs something: the
7 dropped cases and the `TestTui` workaround were both *reasonable responses to a contradictory
packet*, and a single line saying so would have surfaced the packet's error immediately instead of
three commits later.
